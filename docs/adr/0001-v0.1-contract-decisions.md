# ADR 0001: v0.1 Contract Decisions

Status: Accepted

Date: 2026-09-16

## Context

The v0.1 interface needs explicit calendar and age rules so clients can audit
results without inferring regional, religious, or family-specific conventions.

## Decisions

### Supported Range

The canonical supported range is the normalized Gregorian period
`1900-01-01` through `2100-12-31`, inclusive. Chinese lunar dates are accepted
when their conversion resolves inside that period. This permits the boundary
lunar date `1899-12-01`, which corresponds to `1900-01-01`.

Dates outside this period return `DATE_OUT_OF_RANGE`; no best-effort result is
returned.

### Leap-Month Birthday Default

`regular_month` is the default. If the target year has the matching leap month,
the birthday uses it. Otherwise, the birthday uses the regular month and same
day.

`skip` and `strict` are explicit alternatives and are never selected
implicitly.

### Nominal Age

The only v0.1 nominal-age rule is `lunar_new_year`:

```text
current Chinese lunar year - birth Chinese lunar year + 1
```

The rule does not silently substitute `lichun`.

### Timezone

Conversion and age calculations operate on civil dates. A timezone is used
only to resolve today's date when `as_of_date` is omitted. The default is
`Asia/Shanghai`.

### Transport

v0.1 uses stdio only. A stateless Streamable HTTP transport is deferred until a
remote or multi-client deployment is an actual requirement.

### Birthday Range

`calendar_list_birthdays` accepts at most 100 inclusive calendar years. Results
are always bounded and `has_more` is `false` for a valid request.

### Conversion Library

`lunar-javascript` `1.7.7` is the conversion adapter implementation and is
pinned by `package-lock.json`.

## Independent Verification

The mandatory v0.1 fixtures were checked against Node.js ICU using the
`zh-CN-u-ca-chinese` calendar. The cross-check included:

- Gregorian `2005-06-25` to lunar `2005-05-19`
- Gregorian `2026-07-03` to lunar `2026-05-19`
- Gregorian `2023-04-05` to lunar leap `2023-02-15`
- Chinese New Year `2026-02-17`
- Boundary conversions at Gregorian `1900-01-31` and `2100-12-31`

## Consequences

- Tool responses expose intermediate Gregorian dates for audit.
- Unsupported calendars, age systems, policies, and invalid lunar dates return
  stable machine-readable errors.
- Expanding the supported range or adding calendars requires explicit fixtures
  and a new contract decision.
